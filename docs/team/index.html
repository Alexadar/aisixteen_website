What it is

What it is

Fantastic Team is a program built on fantastic, the kernel of agents. One headless binary does the work. A web UI is opt-in on a local port, and a desktop app wraps that UI.

It is not only for code. A task is any piece of work that can be described exactly and checked. Each task says what to read, what to produce and how to check it.

  • Code
  • Documentation
  • Research
  • Triage
  • Data
  • Review
  • Translation
  • Ports

The team does not merge. When work belongs in a repository it opens a draft pull request, and a person reviews and merges it.

Run it

Two ways to run

The same program, started two ways. What differs is who defines the agents.

Only what you define

The CLI

The fantastic_team binary adds no coding agent of its own. It runs only the agents your team.yaml defines. A team.yaml with no templates and no first agent is valid and starts only the system agents: the dispatcher, the tools and the queue.

  • No default lead, no default workers
  • Fully headless unless you pass --port or --tui
  • Scripts render a task file for whatever agents your file defines

A roles preset

The app

The desktop app ships a preset: a lead plus roles. When it starts a team in a folder with no team.yaml, it writes the preset and the role cards there once.

  • The preset is an ordinary team.yaml: edit it
  • The app never overwrites it
  • The lead grows the agents it needs through the roles registry

Inside

How it works

A lead plans, a registry says which agents may exist, and a task registry records who holds what. Nothing is hidden in code: the agents, their models and their directives come from configuration.

  1. Task source
  2. Task registry
  3. Lead
  4. Roles registry
  5. Workers
  6. Draft pull request

Workers hold no forge credentials. Delivery goes through a connector agent that owns the credentials and the rules.

1

A lead and a roles registry

The lead is an AI agent configured in team.yaml, working from a directive. It starts every agent with spawn on the roles registry, after it asks the registry how many agents exist. Roles are cards, one file each: a name, a purpose, a tier and the agents it may call. A tier is the name of a template in team.yaml, so a card never names a model. The registry enforces limits: a spawn past a limit is refused.

2

A task registry between agents and task sources

Tasks live in a task registry that sits between your agents and the places tasks come from, such as GitHub issues. It records each task, who holds it, and every reassignment. It makes no outbound call and syncs nothing by itself: the lead pushes updates to the source through the source's own connector.

3

Versioned reuse

With each task the lead records the versions it was done against: repository, branch and commit, the version of the issue, and the mark an agent was forked from. Before reusing earlier work, the GitHub connector reports what changed since: commits, files and whether the issue changed. The lead decides whether to fork from the earlier mark, to reuse its context and cache.

4

A cadencer

On a timer, the cadencer sends each lead a short digest of its own children. A worker that holds a task and stops making progress is marked as stalled, with its idle time. It is on by default and can be switched off in team.yaml or from the UI.

The interface

The interface

Two columns, in the roles setup. On the left, the team as a tree of agents. On the right, the view of the agent you clicked.

Left
The agent tree: the lead first, then the agents it spawned, indented by depth, with each one's state.
Right
The opened agent's chat. A card appears in the chat where an agent embedded one, and a Canvas button shows when the agent has a canvas. The lead's view also shows the plan, the task registry's rows, above its chat.
Served locally
Start the binary with --port N and the UI is served on 127.0.0.1:N. Nothing is exposed beyond your machine.
Wrapped by the app
The desktop app is a thin window over that same page. It has no logic of its own.

Compared

How it differs

Any model, with your own keys

Workers are fantastic AI agents: Anthropic models over the API with your own key, or local models (vLLM, llama.cpp) on your own GPU. Mix them, and compare them on the same tasks.

Cost measured per task

Each task records its worker, model, time, tokens and cost, computed from the prices in the template. Compare lanes on what a task really costs.

Self-hosted

You run the binary. It can run detached on a box with a GPU while you attach from a laptop over SSH, with the keys passed into memory at start and bound to loopback only.

Workers hold no secrets

Credentials live in the credential store, and workers run commands through a restricted exec: no forge login, no keys in the environment, and forge CLIs refused. This is an early, clear refusal, not an OS sandbox, so run the team as a separate user or in a container.

Two builds

The general build gives workers stock exec. The GitHub build applies a patch so workers cannot reach forge CLIs, git push or credentials; every GitHub action goes through the connector.

Start

Start

There are no releases yet, so you build from source. You need git and a Rust toolchain on Linux or macOS. The run was verified on Linux only.

  1. 1

    Build from source

    git clone https://github.com/aisixteen/fantastic_team
cd fantastic_team
sh scripts/build.sh
./target/release/fantastic_team --help

    For the GitHub build, run sh scripts/build-github.sh instead.

  2. 2

    Write a team.yaml

    templates:
  writer:
    handler_module: anthropic_backend
    model: example-model
    endpoint: https://api.example.com/v1
    credentials:
      store: credentials
      ref: EXAMPLE_KEY
first_agent:
  id: lead
  template: writer
  directive_file: lead.md
queue:
  id: queue

    A team is a folder with a team.yaml. Values for keys are never in the file, only their names. examples/team.yaml in the repo is a complete config.

  3. 3

    Register the GitHub App

    ./target/release/fantastic_team setup github --name NAME

    Optional, and only needed for pull requests, comments, labels and reading issues. It opens a local page, GitHub redirects back, and the key goes to the credential store, never to a file or the screen. Add --org ORG to create the app under an organization.

  4. 4

    Run it and hand it a first task

    ./target/release/fantastic_team --dir ./my-team --port 8123

    In the repo the team serves, label an issue team-ready and add a comment that starts with ## SPEC and holds the task. The label and the comment must come from the maintainer (the comment may also come from your GitHub App); others are ignored. The team opens a draft pull request. You review it on GitHub; merging stays with you.
